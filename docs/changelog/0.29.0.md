# Nexora 0.29.0

发布日期：2026-08-06

## 摘要

本版本重建 Nexora 框架 SQLx 迁移边界。宿主不再读取并合并框架 migration，而是把自己创建
的唯一 `PgPool` 借给新的 `nexora::server::migrate(&PgPool)`。Nexora 使用 SQLx 0.9 原生
`Migrator`，自动创建 `nexora` schema，并把框架历史固定记录在
`nexora._sqlx_migrations`；应用迁移随后使用同一个连接池和自己的独立历史执行。

处理人：[@Jixiangup](https://github.com/Jixiangup)

关联 Issue/PR：无

## Added

- 新增 `nexora::server::migrate(pool: &PgPool) -> Result<(), MigrationError>`；公开中文 rustdoc
  说明连接池所有权、执行顺序、副作用与错误条件，`MigrationError` 保留 SQLx 原始错误链。
  — 处理人：[@Jixiangup](https://github.com/Jixiangup)
- 新增四段可逆 timestamp 基线：Account 身份与初始化、RBAC 授权关系、数据库保护函数与
  触发器、系统角色与权限目录。所有表、列、枚举、具名约束、索引、函数和触发器均带完整
  `COMMENT`。— 处理人：[@Jixiangup](https://github.com/Jixiangup)
- 新增 `manage-sqlx-migrations` Skill 和标准数据库测试包装器。包装器只从项目
  `config/server.toml` 在当前进程派生 `DATABASE_URL`，允许 SQLx 管理隔离测试库，并精确
  清理本次失败遗留。— 处理人：[@Jixiangup](https://github.com/Jixiangup)
- Account workspace 脚手架现在生成 `crates/migrate/migrations`、根 `sqlx.toml`、最小应用
  Migrator、保留 `#[sqlx::test]` 的测试模板和 Nexora → 应用的迁移启动顺序。— 处理人：
  [@Jixiangup](https://github.com/Jixiangup)

## Changed

- Nexora 框架迁移历史固定为 `nexora._sqlx_migrations`；生成应用默认使用
  `public._sqlx_migrations`。两类迁移只共享宿主唯一 `PgPool`，不再合并、重编号或协调
  checksum。— 处理人：[@Jixiangup](https://github.com/Jixiangup)
- 框架迁移历史按 v0.28.0 最终数据库结构重新建立，不保留中间字段、已替换对象、旧数据回填、
  旧版本映射或 checksum 兼容逻辑。— 处理人：[@Jixiangup](https://github.com/Jixiangup)
- `AGENTS.md`、数据库与 Axum Skills、脚手架示例和中英文文档统一要求只用
  `sqlx migrate add <module>_<description>` 创建可逆 timestamp 迁移，并保留所有数据库测试
  与 `#[sqlx::test]`。— 处理人：[@Jixiangup](https://github.com/Jixiangup)

## Removed

- 删除 `nexora::server::migrations()` 以及向宿主暴露框架 migration 元数据的公开契约。
  — 处理人：[@Jixiangup](https://github.com/Jixiangup)
- 删除 `MigrationPlan`、跨来源版本冲突协调、迁移重编号、checksum 修复与旧历史兼容逻辑。
  — 处理人：[@Jixiangup](https://github.com/Jixiangup)

## 兼容性与破坏性变更

v0.29.0 不支持旧数据库原地升级。v0.28.0 及更早版本的 `_sqlx_migrations` 历史与新基线不
兼容；所有下游必须先保护需要保留的数据，然后清库重建，依次执行 Nexora 和应用迁移。不要
删除旧历史表后在原库强行运行新基线，这会与既有 Account 对象冲突，也不属于受支持的升级
路径。

旧宿主代码读取并合并两套 migration：

```rust
let framework = nexora::server::migrations();
let migrations = merge_and_reject_duplicate_versions(framework, application_migrations)?;
sqlx::migrate::Migrator::with_migrations(migrations)
    .run(&pool)
    .await?;
```

新宿主代码使用同一个池顺序执行两个独立入口：

```rust
nexora::server::migrate(&pool).await?;
application_migrate::migrate(&pool).await?;

let mut server = nexora::Server::new();
server.initialize(&settings, &pool, setup_secret).await?;
```

## 从 0.28.0 升级

1. 在停机窗口备份所有必须保留的业务数据和当前数据库快照；确认恢复步骤可用。
2. 把所有 Nexora workspace 依赖更新为 `0.29.0` 或 Git tag `v0.29.0`，重新生成 lockfile，
   并重新安装 `v0.29.0` CLI。
3. 删除宿主的 migration 合并、跨来源版本冲突和 checksum 兼容代码；改为先调用
   `nexora::server::migrate(&pool)`，再运行应用自己的 Migrator。
4. 清库重建，不尝试在旧 Account schema 或旧 `_sqlx_migrations` 历史上原地升级；重新运行
   Nexora 与应用迁移后，通过受审计的业务导入流程恢复允许保留的数据。
5. 同步 `manage-sqlx-migrations`、相关数据库/Axum Skill、根 `sqlx.toml` 和数据库测试包装器。
   新迁移只能由 `sqlx migrate add` 创建。

回滚到 v0.28.0 时，不要让 v0.28.0 代码复用已经由 v0.29.0 建立的数据库。恢复升级前数据库
快照，同时恢复 v0.28.0 二进制、依赖和 lockfile；v0.29.0 的 down migration 不是旧历史的
兼容转换工具。
