# Nexora 0.38.1

发布日期：2026-08-17

## 摘要

本补丁修正 0.38.0 将 ZITADEL introspection Client ID/Secret 设为启动必填项的问题。服务端现在
始终保留 JWT discovery/JWKS 校验；只有同时提供并通过 Provider 探测的 Client ID/Secret 才启用
PAT/opaque token。缺失、不完整或被拒绝的凭据会安全降级为 JWT-only，临时故障不会阻止 JWT
启动，并会在后续 opaque/PAT 操作中自动重试。

处理人：[@Jixiangup](https://github.com/Jixiangup)

关联 Issue/PR：无

## Fixed

- `introspection_client_id` 与 `introspection_client_secret` 改为可选反序列化字段；两项都省略时
  不告警并进入 JWT-only，单边配置或 Provider 返回 401 时告警并降级，而不是阻止服务启动。
  — 处理人：[@Jixiangup](https://github.com/Jixiangup)
- 组合 verifier 使用固定无效 token 探测 `/oauth/v2/introspect`：有效 Basic 凭据即使得到
  `active=false` 也视为能力可用；网络错误、无效 JSON 或 5xx 被分类为临时故障并保留配置，恢复后
  无需重启。— 处理人：[@Jixiangup](https://github.com/Jixiangup)
- PAT 创建会在调用 Provider 前实时确认 introspection 可用，并在 Provider 返回实际 PAT 后强制
  校验 active、issuer、audience、有效期和服务账号 subject。校验失败时撤销 Provider PAT，且不
  持久化或交付明文。— 处理人：[@Jixiangup](https://github.com/Jixiangup)

## Changed

- 未启用 introspection 时，opaque Bearer token 返回 `401 invalid_access_token`，创建 PAT 返回
  `409 personal_access_token_unavailable`；已配置凭据但 Provider 临时不可用时保持
  `503 token_introspection_unavailable`。Client Credentials 与 JWT 不依赖 introspection。
  — 处理人：[@Jixiangup](https://github.com/Jixiangup)
- 配置示例与 Account workspace 脚手架默认注释掉可选 introspection 字段，并明确不需要
  `mode = "client_secret_basic"`；配置时只需成对提供有效 Client ID/Secret。
  — 处理人：[@Jixiangup](https://github.com/Jixiangup)

## Security

- 探测与运行时错误只记录脱敏分类，不输出 Client Secret、Authorization 或 token。PAT 只有在
  创建后 introspection 与服务账号 subject 均通过时才会一次性交付。
  — 处理人：[@Jixiangup](https://github.com/Jixiangup)

## 兼容性与破坏性变更

- 本版本没有数据库迁移、HTTP 路径、请求/响应字段、桌面 UI 或生成项目结构变更。
- 0.38.0 的完整 introspection 配置继续有效；本版本只放宽配置要求并增加安全探测，不要求删除
  已有字段。直接实现 `AccessTokenVerifier` 的下游无需修改：新增 opaque 能力方法都有 JWT-only
  默认实现。
- 新增的 `409 personal_access_token_unavailable` 只出现在请求创建 PAT、但当前部署未启用有效
  introspection 的场景。已有 PAT 的列出、协调和撤销接口保持可用。
- 本版本没有修改 `.agents/skills` 或宏规则，下游无需同步 Skill；Account 脚手架只调整了配置
  示例注释。

## 从 0.38.0 升级

1. 把全部 Nexora workspace 依赖与 CLI 切换到 Git tag `v0.38.1`，删除临时 path/patch 并重新生成
   `Cargo.lock`。
2. 只使用 JWT/Client Credentials 的部署可以同时省略 `introspection_client_id` 与
   `introspection_client_secret`；不要增加 `mode` 字段。
3. 需要 PAT/opaque token 的部署应成对保留有效 Client ID/Secret，并通过环境变量或密钥系统注入
   Secret。服务启动时会探测凭据，PAT 创建前后也会实时校验。
4. 无需执行新增数据库迁移。按现有顺序运行框架与应用 Migrator 后，验证 JWT 登录、Client
   Credentials、PAT 创建、opaque Bearer 认证以及 Provider 临时故障恢复。

回滚到 0.38.0 不需要数据库回滚，但必须恢复两项非空 introspection 配置，否则 0.38.0 会初始化
失败。0.38.1 创建的 Provider 凭据不会因代码回滚自动撤销；如需删除，仍应通过凭据撤销接口或
ZITADEL 完成。
