# Nexora 0.39.0

Release date: 2026-08-17

## Summary

Account now supports internal service principals that are not bound to an identity provider. They
retain the existing `service_account` user type and use `identity_id = null` to explicitly mean
“does not authenticate.” This lets audit records reference a stable local actor without exposing that
actor in normal user management or sending it into ZITADEL credential flows.

Owner: [@Jixiangup](https://github.com/Jixiangup)

Related Issue/PR: none

## Added

- Added a reversible SQLx migration that permits `account.users.identity_id` to be null while a
  database constraint continues to require every human account to have a non-null Provider identity.
  — Owner: [@Jixiangup](https://github.com/Jixiangup)
- `User` and `UserResponse` now expose an optional `identity_id`. The HTTP field remains present and
  is `null` for internal service principals. — Owner: [@Jixiangup](https://github.com/Jixiangup)

## Changed

- The ordinary `GET /users` collection and default user-management UI exclude internal principals
  whose `identity_id` is null. Existing human users and Provider machine users are unchanged.
  — Owner: [@Jixiangup](https://github.com/Jixiangup)
- Provider profile and credential operations now return the stable
  `409 internal_service_account` error for an internal principal, before accessing ZITADEL.
  — Owner: [@Jixiangup](https://github.com/Jixiangup)

## Compatibility and breaking changes

- Public Rust fields `User.identity_id` and `UserResponse.identity_id` changed from `String` to
  `Option<String>`. Downstream Rust code that reads these fields must handle `None`.
- The HTTP `User.identity_id` field remains required, but its schema changed from `string` to
  `string | null`. Existing human and Provider service accounts still return a string.
- No `audit` user type was added. Internal principals remain `service_account` rows; the presence of
  `identity_id` distinguishes a Provider account from a local principal.
- The migration only relaxes column nullability and adds the human-identity constraint. It does not
  rewrite or delete existing rows, and local-ID audit foreign keys remain valid.
- There are no new settings, permissions, desktop controls, macros, Skills, or scaffold rules.

## Upgrading from 0.38.2

1. Move every Nexora workspace dependency to Git tag `v0.39.0`, regenerate `Cargo.lock`, and keep the
   desktop and server on the same tag.
2. At startup, run `nexora::server::migrate(&pool)` on the host's single `PgPool` before running the
   application's own migrations.
3. An application migration may set `identity_id` to `NULL` for an internal service account that
   never logs in and owns no Secret/PAT. Continue to use the eight-character local user `id` for audit
   references rather than a Provider identity.
4. Verify that the internal principal is absent from `GET /users` and the default user page while
   human accounts and real Provider service accounts remain manageable.

Before rolling back to 0.38.2, remove internal principals or bind every row with
`identity_id = NULL` to a valid Provider identity. The down migration deliberately fails while null
identities remain so that audit data cannot be silently damaged.

## Validation

The following gates ran and passed:

- A `semver`-based test confirms that `0.39.0` is strictly greater than `0.38.2`
- `cargo fmt --all --check`
- `cargo test --workspace --all-targets`
- `cargo clippy --workspace --all-targets --all-features -- -D warnings`
- `cargo run -p cli -- lint --workspace . --deny-warnings`
- `bash scripts/check-scaffold-consumer.sh`
- `cd docs && bun install --frozen-lockfile && bun run build`
- `bunx @redocly/cli lint docs/public/openapi.yaml --skip-rule operation-4xx-response`

The database-feature migration and Account regression tests compile. Running them through the
standard `config/server.toml` was blocked because the configured PostgreSQL instance reports that its
`mes` base database does not exist. Database-free migration tests cover registration, reversibility,
and the human-identity constraint. Once the standard database is restored, rerun the human-null
constraint, internal-principal list-filter, and `409 internal_service_account` HTTP regressions.

Signing, notarization, object storage, and CLI self-update assets continue through the tag-triggered
GitHub Actions release workflow. Source dependencies can upgrade as soon as the `v0.39.0` tag is
pushed and do not need to wait for those binary publishing jobs.
