# Nexora 0.29.0

Release date: 2026-08-06

## Summary

This release rebuilds Nexora's SQLx migration boundary. Hosts no longer read and merge framework
migration metadata. They lend their single `PgPool` to the new
`nexora::server::migrate(&PgPool)`. Nexora uses SQLx 0.9's native Migrator, creates the `nexora`
schema automatically, and records framework history in `nexora._sqlx_migrations`. Application
migrations then run against the same pool with an independent history.

Owner: [@Jixiangup](https://github.com/Jixiangup)

Related issue/PR: none

## Added

- Added `nexora::server::migrate(pool: &PgPool) -> Result<(), MigrationError>`. Its public Chinese
  rustdoc documents pool ownership, ordering, side effects, and failures, and `MigrationError`
  preserves the original SQLx error chain. — Owner: [@Jixiangup](https://github.com/Jixiangup)
- Added four reversible timestamp baselines: Account identity and initialization, RBAC relations,
  database protection functions and triggers, and the system role/permission catalog. Every table,
  column, enum, named constraint, index, function, and trigger has a complete `COMMENT`. — Owner:
  [@Jixiangup](https://github.com/Jixiangup)
- Added the `manage-sqlx-migrations` Skill and a standard database-test wrapper. It derives
  `DATABASE_URL` in the current process only from project `config/server.toml`, allows SQLx to
  manage isolated databases, and precisely cleans leftovers from the current failed run. — Owner:
  [@Jixiangup](https://github.com/Jixiangup)
- Account workspace scaffolds now include `crates/migrate/migrations`, root `sqlx.toml`, a minimal
  application Migrator, a database test template that retains `#[sqlx::test]`, and the Nexora →
  application startup order. — Owner: [@Jixiangup](https://github.com/Jixiangup)

## Changed

- Nexora framework history is fixed at `nexora._sqlx_migrations`; generated applications default
  to `public._sqlx_migrations`. The two sources share only the host's one `PgPool` and are no longer
  merged, renumbered, or checksum-coordinated. — Owner: [@Jixiangup](https://github.com/Jixiangup)
- Framework migration history was rebuilt from the final v0.28.0 database structure. It contains no
  intermediate columns, superseded objects, old-data backfills, legacy version mappings, or
  checksum compatibility logic. — Owner: [@Jixiangup](https://github.com/Jixiangup)
- `AGENTS.md`, database/Axum Skills, scaffolds, examples, and bilingual documentation now require
  `sqlx migrate add <module>_<description>` for reversible timestamp migrations and preserve every
  database test and `#[sqlx::test]`. — Owner: [@Jixiangup](https://github.com/Jixiangup)

## Removed

- Removed `nexora::server::migrations()` and the public contract that exposed framework migration
  metadata to hosts. — Owner: [@Jixiangup](https://github.com/Jixiangup)
- Removed `MigrationPlan`, cross-source version coordination, migration renumbering, checksum
  repair, and legacy-history compatibility logic. — Owner: [@Jixiangup](https://github.com/Jixiangup)

## Compatibility and breaking changes

v0.29.0 does not support in-place upgrades of old databases. The v0.28.0 and earlier
`_sqlx_migrations` history is incompatible with this baseline. Every downstream application must
protect required data, rebuild the database from empty, and run Nexora then application migrations.
Do not delete the old history table and force the new baseline over existing Account objects; that
will conflict and is not a supported upgrade path.

Old host code read and merged both migration sources:

```rust
let framework = nexora::server::migrations();
let migrations = merge_and_reject_duplicate_versions(framework, application_migrations)?;
sqlx::migrate::Migrator::with_migrations(migrations)
    .run(&pool)
    .await?;
```

New host code runs two independent entry points in order against the same pool:

```rust
nexora::server::migrate(&pool).await?;
application_migrate::migrate(&pool).await?;

let mut server = nexora::Server::new();
server.initialize(&settings, &pool, setup_secret).await?;
```

## Upgrading from 0.28.0

1. During downtime, back up every required business record and the current database snapshot, and
   verify the restore procedure.
2. Update all Nexora workspace dependencies to `0.29.0` or Git tag `v0.29.0`, regenerate lockfiles,
   and reinstall the v0.29.0 CLI.
3. Remove host migration merging, cross-source version-conflict, and checksum-compatibility code.
   Call `nexora::server::migrate(&pool)` first, then the application Migrator.
4. Rebuild the database from empty. Do not migrate in place over the old Account schema or old
   `_sqlx_migrations` history. Run both migration sources, then restore allowed data through an
   audited business import.
5. Sync `manage-sqlx-migrations`, related database/Axum Skills, root `sqlx.toml`, and the database
   test wrapper. Create every new migration with `sqlx migrate add`.

To roll back to v0.28.0, do not point v0.28.0 code at a database built by v0.29.0. Restore the
pre-upgrade database snapshot together with the v0.28.0 binary, dependencies, and lockfile. The
v0.29.0 down migrations are not a legacy-history conversion tool.
