# Nexora 0.34.0

Release date: 2026-08-11

## Summary

This release changes Nexora desktop's default window hosting model to in-process multi-window.
The main window, extra Shells, the unique Settings window, and registered Windows now share one
GPUI application process, application Globals, business models, and caches by default, avoiding a
complete application-runtime initialization for every window. It also fixes stale session recovery
when a child window is closed individually and the application exits before the main process has
consumed its `WindowClosed` event.

Handler: [@Jixiangup](https://github.com/Jixiangup)

Related Issue/PR: none

## Changed

- `ApplicationOptions::default()` now sets `subprocess_windows` to `false`. Extra Shells, Settings,
  and registered Windows are created through `App::open_window` in the same GPUI event loop, so
  `Application::initialize`, Account, Preferences, Updater, business Globals, and shared Models need
  only one runtime. — Handler: [@Jixiangup](https://github.com/Jixiangup)
- Each window continues to own its Shell, Feature UI entities, tabs, focus, input, subscriptions,
  tasks, and form drafts. The framework does not reuse one UI entity across windows. Large business
  collections and caches that need cross-window sharing should live in an application Global or
  shared Model. — Handler: [@Jixiangup](https://github.com/Jixiangup)
- `.subprocess_windows(true)` retains managed-child hosting for applications that explicitly need
  fault isolation, security isolation, or an independent service lifecycle. Singleton enforcement,
  complete multi-window behavior, session restoration, unique Settings, registered Windows, and
  tray window-group commands remain available in both modes.
  — Handler: [@Jixiangup](https://github.com/Jixiangup)
- The `develop-nexora-apps` and `gpui-desktop-development` Skills, their scaffold-embedded copies,
  and the Chinese and English desktop documentation now describe the new default and shared-state
  boundary. — Handler: [@Jixiangup](https://github.com/Jixiangup)

## Fixed

- During coordinated exit, the main process first publishes the exit reason, waits for managed
  children to submit their final window-session patches, synchronously drains queued preference
  patches, session patches, and `WindowClosed`, and only then flushes the authoritative snapshot.
  Individually closed windows no longer reappear, while windows still open at exit remain restorable.
  — Handler: [@Jixiangup](https://github.com/Jixiangup)
- New managed-child window creation is no longer honored during exit. Sessions for windows that were
  never actually created are removed from the final snapshot instead of reappearing on the next
  launch. — Handler: [@Jixiangup](https://github.com/Jixiangup)
- Regression coverage now includes the default in-process mode, the explicit subprocess opt-in, and
  ordering where a final session patch is followed by an individual window close.
  — Handler: [@Jixiangup](https://github.com/Jixiangup)

## Compatibility and breaking changes

- This is a default-configuration behavior change in the `0.x` series. Applications that do not set
  `subprocess_windows` move from multiple managed processes to one OS process. Applications that
  depend on process-level fault, security, or service-lifecycle isolation must explicitly call
  `.subprocess_windows(true)`.
- Applications that already set `.subprocess_windows(false)` or `.subprocess_windows(true)` retain
  their choice. Defaults for `single_instance`, `restore_window_sessions`, and `tray_enabled` are
  unchanged.
- No public Rust API is removed or renamed, and there are no `workspace.toml` schema, HTTP API,
  Account DTO, SQLx migration, database baseline, or Updater protocol changes. No data or
  configuration migration is required.
- The default in-process mode shares application-level state but cannot automatically merge business
  data that downstream Features copy into their own fields. Move genuinely cross-window data into an
  application Global or shared Model while keeping window-local UI state local.

## Upgrading from 0.33.2

1. Update every Nexora dependency and the CLI to `v0.34.0`, then refresh the lockfile.
2. Applications accepting the default in-process multi-window model need no new option. Check that
   application-wide business data is owned by a Global or shared Model rather than copied into each
   window's Feature.
3. Applications requiring managed-process isolation must explicitly add
   `.subprocess_windows(true)` to `ApplicationOptions`. Do not disable singleton enforcement,
   session restoration, or the tray at the same time unless the product does not need them.
4. Synchronize `.agents/skills/develop-nexora-apps/SKILL.md` and
   `.agents/skills/gpui-desktop-development/SKILL.md`. Scaffold-embedded Skills are updated, so newly
   generated projects receive the new guidance automatically.
5. On each target platform, verify multi-window creation, individual close followed by immediate
   exit, exit while windows remain open, restart restoration, Settings uniqueness, registered
   Windows, duplicate-launch activation, and tray window-group commands.

Rolling back to v0.33.2 requires no database or configuration migration. To keep in-process
multi-window hosting after rollback, retain an explicit `.subprocess_windows(false)` in application
code; otherwise v0.33.2 restores managed-child hosting by default.

## Validation

Completed successfully before publishing:

- Used a version parser to confirm that `0.34.0` is strictly newer than the latest published version,
  `0.33.2`
- `cargo fmt --all --check`
- `cargo test --workspace --all-targets`
- `cargo clippy --workspace --all-targets --all-features -- -D warnings`
- `cargo run -p cli -- lint --workspace . --deny-warnings`
- `bash scripts/check-scaffold-consumer.sh`
- `cd docs && bun install --frozen-lockfile && bun run build`

The scaffold check resolves dependencies without a `Cargo.lock` for both a standard desktop project
and an Account full-stack project, then compiles the desktop, server, and migration test targets.
Manual Windows/Linux GUI acceptance was not run from the current macOS environment, and no external
PostgreSQL, OIDC, signing, notarization, or S3/RustFS publishing environment was used. This release
does not change those protocols or integration boundaries. Downstream applications should measure
multi-window process count and RSS with representative business data; the release gate does not
claim a fixed memory threshold.
