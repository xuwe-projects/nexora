# Nexora 0.38.2

Release date: 2026-08-17

## Summary

This patch fixes Account user-list parsing for valid URL query parameters. A request such as
`GET /users?page=1&page_size=25` no longer returns `400 invalid_query_parameter`, allowing the default
user-management DataTable to load and display its rows.

Owner: [@Jixiangup](https://github.com/Jixiangup)

Related Issue/PR: none

## Fixed

- `UserListQuery` now deserializes through a dedicated flat wire model. This prevents Serde
  `flatten` buffering from passing the URL-encoded `page` and `page_size` strings to a later `u32`
  deserializer. Axum `Query` now accepts both default pagination and complete `keyword`, `status`, and
  `user_type` filters. — Owner: [@Jixiangup](https://github.com/Jixiangup)
- Added database-free Axum Router regression coverage for default pagination, complete filters, and
  continued `400 invalid_query_parameter` rejection of unknown query fields.
  — Owner: [@Jixiangup](https://github.com/Jixiangup)

## Compatibility and breaking changes

- The HTTP method, path, and wire parameters are unchanged: `GET /users` still accepts flat `page`,
  `page_size`, `keyword`, `status`, and `user_type` parameters.
- The public Rust API is unchanged. Callers still use `UserListQuery.page: PageQuery`; serialization,
  defaults, enum values, and unknown-field rejection remain intact.
- There is no database migration, configuration, desktop UI, permission, response-shape, or generated
  project structure change.
- `.agents/skills`, macro rules, and scaffold constraints are unchanged, so downstream projects do
  not need to synchronize a Skill.

## Upgrading from 0.38.1

1. Move all Nexora workspace dependencies and the CLI to Git tag `v0.38.2`, remove temporary
   path/patch overrides, and regenerate `Cargo.lock`.
2. Rebuild and deploy the server. The fix is in the Account query contract's server-side
   deserialization path and takes effect after the server restarts. Keep desktop and server on the
   same tag where practical.
3. No `GET /users` caller, configuration, database, or migration change is required.
4. Verify default pagination, keyword, status, and user-type filters, plus the unknown-query error.

Rolling back to 0.38.1 requires no database or configuration rollback, but reintroduces the
`400 invalid_query_parameter` failure for valid user-list pagination requests.

## Validation

The following gates were run and passed:

- A `semver`-based test confirms that `0.38.2` is strictly greater than `0.38.1`
- `cargo fmt --all --check`
- `cargo test --workspace --all-targets`
- `cargo clippy --workspace --all-targets --all-features -- -D warnings`
- `cargo run -p cli -- lint --workspace . --deny-warnings`
- `bash scripts/check-scaffold-consumer.sh`, including a lockfile-free single-package desktop project
  and compilation of the Account workspace server and migration crate
- `cd docs && bun install --frozen-lockfile && bun run build`
- `bunx @redocly/cli lint docs/public/openapi.yaml --skip-rule operation-4xx-response`

The regression test first confirmed that default pagination and complete filters both returned `400`
before the fix; the same requests return `200` afterward, while unknown fields retain the stable
`400 invalid_query_parameter` contract. This change does not access PostgreSQL, OIDC, or ZITADEL, so
those external-environment tests are not applicable. Signing, notarization, object storage, and
binary-release CI do not block this source upgrade.
