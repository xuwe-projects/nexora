# Nexora 0.33.2

Release date: 2026-08-11

## Summary

This patch fixes a Windows/MSVC build failure in the `configuration` crate. Enabling `windows/std`
allows `windows_result::Error` to remain the source of the existing `std::io::Error`. It also fixes
Windows singleton startup when `ERROR_LOCK_VIOLATION` is not mapped to `WouldBlock`, and makes the
GitHub Release workflow safely rerunnable when the corresponding Release already exists.

Handler: [@Jixiangup](https://github.com/Jixiangup)

Related Issue/PR: none

## Fixed

- The Windows-only `windows` dependency of `configuration` now enables `std`, allowing the existing
  `.map_err(std::io::Error::other)` conversion to satisfy the `std::error::Error` bound while
  preserving the underlying Windows error type. — Handler: [@Jixiangup](https://github.com/Jixiangup)
- Desktop singleton startup now compares against the standard lock-contention error supplied by
  `fs2`. Windows `ERROR_LOCK_VIOLATION (33)` no longer aborts a secondary launch when Rust maps it
  to `ErrorKind::Uncategorized`; the existing main process receives the activation request.
  — Handler: [@Jixiangup](https://github.com/Jixiangup)
- The GitHub Release job now creates a draft only when no Release exists. Existing draft or public
  Releases have their full asset set overwritten and their title and notes synchronized, allowing
  tag publishing to be rerun safely. — Handler: [@Jixiangup](https://github.com/Jixiangup)

## Compatibility and breaking changes

- There are no breaking public Rust API, configuration format, configuration path, HTTP API,
  Account DTO, SQLx migration, database baseline, or Updater protocol changes.
- Windows atomic configuration replacement still uses `MoveFileExW`, `MOVEFILE_REPLACE_EXISTING`,
  and `MOVEFILE_WRITE_THROUGH`; save, update, cross-process locking, temporary-file, and error-source
  semantics are unchanged.
- Desktop singleton identity, runtime directories, lock-file names, the local IPC protocol, and
  public APIs are unchanged. This release only corrects recognition of the existing Windows lock
  contention state.
- `windows/std` is enabled only on the Windows target-specific dependency of `configuration`. The
  workspace dependency still uses `default-features = false`, so other crates do not receive a
  broader feature set.

## Upgrading from 0.33.1

1. Update every Nexora dependency and the CLI to `v0.33.2`, then refresh the lockfile.
2. Rebuild Windows/MSVC applications; no configuration file, environment variable, or application
   code change is required. Secondary launches will activate the existing main process instead of
   reporting normal lock contention as an I/O error.
3. This release does not change Skills, scaffold generation rules, or macro requirements, so
   downstream projects do not need to synchronize `.agents/skills`.

Rolling back requires no database or configuration migration, but Windows/MSVC builds will again
encounter `windows_result::Error: StdError is not satisfied`, and secondary desktop launches may
again report `ERROR_LOCK_VIOLATION` as an I/O failure. The release workflow will also return to the
previous behavior that cannot safely replenish assets on an existing Release.

## Validation

Completed successfully before publishing:

- Used the Node `semver` parser to confirm that `0.33.2` is strictly newer than the latest published
  version, `0.33.1`
- `cargo tree -p configuration --target x86_64-pc-windows-msvc -e features -i windows@0.61.3`
- `cargo tree -p configuration --target x86_64-pc-windows-msvc -e features -i windows-result@0.3.4`
- `cargo check -p configuration --all-targets --locked`
- `cargo test -p configuration --all-targets --locked`
- `cargo test -p desktop --test process second_bootstrap_activates_existing_main_process --locked -- --exact --nocapture`
- `cargo fmt --all --check`
- `cargo test -p changelog --all-targets --locked`
- `cargo test --workspace --all-targets`
- `cargo clippy --workspace --all-targets --all-features -- -D warnings`
- `cargo run -p cli -- lint --workspace . --deny-warnings`
- `bash scripts/check-scaffold-consumer.sh`
- `cd docs && bun install --frozen-lockfile && bun run build`

Full workspace and scaffold-consumer validation used the official `protoc 34.0` and the locally
installed `protoc-gen-rust-grpc`. The scaffold check resolved dependencies without a `Cargo.lock`
for both a standard desktop project and an Account full-stack project, then compiled the desktop,
server, and migration test targets. Documentation built successfully with Bun 1.3.14 and VitePress
1.6.4.

Three workspace tests that require manually provisioned packaging tools remained ignored by their
existing conditions: two require `NEXORA_TEST_ISCC` to reference a compatible ISCC, and one requires
an explicitly provisioned `rc.exe` and MSVC linker acceptance environment.

The `configuration` build and tests ran in a real Windows/MSVC environment. Manual Linux/macOS
platform acceptance was not run, and no external PostgreSQL, OIDC, signing, notarization, or
S3/RustFS publishing environment was used. This release does not change those protocols or
integration boundaries.
