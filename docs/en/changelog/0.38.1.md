# Nexora 0.38.1

Release date: 2026-08-17

## Summary

This patch corrects the 0.38.0 requirement for ZITADEL introspection Client ID/Secret credentials at
startup. JWT discovery/JWKS verification is now always available. PAT/opaque-token support is enabled
only when both credentials are present and accepted by the Provider. Missing, partial, or rejected
credentials safely select JWT-only mode. A temporary introspection outage does not prevent JWT startup
and is retried by later opaque/PAT operations.

Owner: [@Jixiangup](https://github.com/Jixiangup)

Related Issue/PR: none

## Fixed

- Made `introspection_client_id` and `introspection_client_secret` optional during deserialization.
  Omitting both silently selects JWT-only mode; a partial pair or Provider 401 emits a redacted warning
  and downgrades instead of blocking startup. — Owner: [@Jixiangup](https://github.com/Jixiangup)
- Added a fixed-invalid-token probe for `/oauth/v2/introspect`. A valid Basic credential pair is
  considered usable even when the probe returns `active=false`. Network failures, invalid JSON, and
  5xx responses are temporary failures that retain configuration and recover without restart.
  — Owner: [@Jixiangup](https://github.com/Jixiangup)
- PAT creation now checks introspection before calling the Provider, then forces the actual generated
  PAT through active, issuer, audience, expiry, and service-account-subject validation. Failure revokes
  the Provider PAT and neither persists nor delivers plaintext.
  — Owner: [@Jixiangup](https://github.com/Jixiangup)

## Changed

- Without introspection, opaque Bearer tokens return `401 invalid_access_token` and PAT creation returns
  `409 personal_access_token_unavailable`. A configured but temporarily unavailable Provider continues
  to return `503 token_introspection_unavailable`. Client Credentials and JWTs do not depend on
  introspection. — Owner: [@Jixiangup](https://github.com/Jixiangup)
- Configuration examples and the Account workspace scaffold now comment out the optional introspection
  fields by default and explicitly require no `mode = "client_secret_basic"` setting. Enabling the
  capability only requires a valid Client ID/Secret pair.
  — Owner: [@Jixiangup](https://github.com/Jixiangup)

## Security

- Probe and runtime errors expose only redacted classifications, never the Client Secret,
  Authorization header, or token. A generated PAT is delivered once only after introspection and the
  service-account subject both pass. — Owner: [@Jixiangup](https://github.com/Jixiangup)

## Compatibility and breaking changes

- This release has no database migration, HTTP path, request/response field, desktop UI, or generated
  project structure change.
- A complete 0.38.0 introspection configuration remains valid. This patch only relaxes configuration
  and adds safety probes. Downstream `AccessTokenVerifier` implementations remain source-compatible
  because the new opaque-capability methods have JWT-only defaults.
- The new `409 personal_access_token_unavailable` occurs only when a caller requests PAT creation while
  the deployment has no valid introspection capability. Existing PAT listing, reconciliation, and
  revocation remain available.
- `.agents/skills` and macro rules are unchanged. Downstream projects do not need to synchronize a
  Skill; only the Account scaffold configuration comments changed.

## Upgrading from 0.38.0

1. Move all Nexora workspace dependencies and the CLI to Git tag `v0.38.1`, remove temporary path/patch
   overrides, and regenerate `Cargo.lock`.
2. JWT/Client-Credentials-only deployments may omit both `introspection_client_id` and
   `introspection_client_secret`. Do not add a `mode` field.
3. Deployments that need PAT/opaque tokens should retain a valid Client ID/Secret pair and inject the
   Secret through an environment variable or secret manager. Startup probes the pair, and PAT creation
   validates introspection both before and after Provider creation.
4. There is no new database migration. Run the existing framework and application Migrators in their
   normal order, then verify JWT login, Client Credentials, PAT creation, opaque Bearer authentication,
   and recovery from a temporary Provider outage.

Rolling back to 0.38.0 requires no database rollback, but both non-empty introspection fields must be
restored or 0.38.0 initialization will fail. Provider credentials created under 0.38.1 are not revoked
by a code rollback; remove them through the credential API or ZITADEL when necessary.

## Validation

The following gates were run and passed:

- A `semver`-based test confirms that `0.38.1` is strictly greater than `0.38.0`
- `cargo fmt --all --check`
- `cargo test --workspace --all-targets`
- `cargo clippy --workspace --all-targets --all-features -- -D warnings`
- `cargo run -p cli -- lint --workspace . --deny-warnings`
- `bash scripts/check-scaffold-consumer.sh`, including a lockfile-free single-package desktop project
  and compilation of the Account workspace server and migration crate
- `cd docs && bun install --frozen-lockfile && bun run build`
- `bunx @redocly/cli lint docs/public/openapi.yaml --skip-rule operation-4xx-response`

The base PostgreSQL database in standard `config/server.toml` does not exist. The `database-tests`
targets compile, but isolated `#[sqlx::test]` cases were not run; no alternate database URL or
long-lived test database was used. Live ZITADEL Client ID/Secret, PAT, and introspection end-to-end
network tests were not run. Deterministic loopback tests cover credential probing, JWT-only downgrade,
401/5xx classification, outage recovery, real-time opaque-token verification, and PAT compensation.
Signing, notarization, object storage, and binary-release CI do not block this source upgrade.
