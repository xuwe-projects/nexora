# Nexora 0.42.0

Release date: 2026-08-22

This release gives `stable`, `beta`, and `nightly` mutually exclusive local installation
identities. Installation directories, process singletons, updater state and operation logs,
Account credentials, and user preferences are now isolated by channel. It also adds bounded,
best-effort updater operation logs that cannot affect the update transaction.

## Added

- The CLI now derives `<app_id>.beta` / `<display_name> Beta` for beta and
  `<app_id>.nightly` / `<display_name> Nightly` for nightly from the stable base values. The
  derived identity covers bundle and Setup AppIds, default installation directories, shortcuts
  and distributed artifact names, process singleton and activation IPC, updater state, Account
  credentials, and user preferences. Stable keeps its existing base identity and data locations.

  — Owner: [@Jixiangup](https://github.com/Jixiangup)
  — Related issue/PR: none

- Formal packages now contain a plain-text `nexora-install-identity` marker. The Windows installer
  accepts only an empty directory, a directory carrying the expected identity, or a legacy stable
  directory identified through the same AppId's HKCU uninstall registration. The runtime updater
  also verifies current, staged, and restored pending packages before replacement.

  — Owner: [@Jixiangup](https://github.com/Jixiangup)
  — Related issue/PR: none

- Every updater check, download, or complete update creates an operation session below the current
  channel's `logs` state directory. The main process writes `main.log`, and the installation
  sidecar continues the same session in `sidecar.log`. Only the newest 10 sessions are retained,
  each session is capped at 1 MiB in total, and credential fields and URL query strings are redacted.

  — Owner: [@Jixiangup](https://github.com/Jixiangup)
  — Related issue/PR: none

## Changed

- The trusted release identity embedded in a formal package now takes precedence over
  `ApplicationOptions::application_identity`. The option can still identify development and test
  processes without formal release metadata, but it can no longer rewrite a packaged channel
  identity.

  — Owner: [@Jixiangup](https://github.com/Jixiangup)
  — Related issue/PR: none

- The CLI rejects base `app_id` and optional `updater.app_id` values ending in
  `.beta`/`.nightly`, and base `display_name` values ending in ` Beta`/` Nightly`. This prevents
  double derivation and spoofed channel identities. The Windows installer also stops using the
  shared technical EXE name as a filter for closing applications from other channels.

  — Owner: [@Jixiangup](https://github.com/Jixiangup)
  — Related issue/PR: none

- Updater operation logging is strictly best effort. Failures to create, lock, write, or rotate
  logs only emit a warning and never change the result of checking, downloading, replacing,
  health confirmation, or rollback.

  — Owner: [@Jixiangup](https://github.com/Jixiangup)
  — Related issue/PR: none

## Compatibility and breaking changes

- This is a breaking `MINOR` release in the early-alpha `0.x` line. Stable keeps its existing app
  ID, display name, installation directory, singleton, credentials, preferences, and updater state,
  so it can be upgraded in place.
- Beta and nightly packages built by `v0.41.2` or earlier shared the stable local identity.
  `v0.42.0` does not read, migrate, or delete that legacy data. Beta and nightly users must install
  the new packages into their new channel-specific directories, then sign in and configure their
  preferences again. Do not manually copy credentials, preferences, or updater state between
  channels.
- Existing configuration that embeds `.beta`, `.nightly`, ` Beta`, or ` Nightly` in a base value
  now fails CLI validation. Replace an old value such as `app_id = "com.example.app.beta"` with
  the unsuffixed `app_id = "com.example.app"`; the selected channel derives the suffix.
  `updater.app_id` and `display_name` follow the same rule.
- Runtime `application_identity` overrides no longer affect formal installations. Development and
  test runs without `nexora-release.json` are unchanged. Applications that used a runtime override
  to share a formal installation identity must build the intended channel separately.
- Rolling back to `v0.41.2` or earlier does not expose the newly isolated beta/nightly data and may
  return to the old shared identity. Keep the new channel directories intact and do not overwrite
  them with an old installer. Stable's in-place rollback path is unaffected.
- The `nexora-release.json` schema, signed manifest, object-storage layout, HTTP API, OpenAPI
  contract, and database structures are unchanged. `docs/public/openapi.yaml` only updates its
  release metadata version to `0.42.0`.

## Upgrading from 0.41.2

1. Update every Nexora Git dependency and CLI installation tag from `v0.41.2` to `v0.42.0`. Run
   `cargo update` and verify that workspace packages resolve to the new version.
2. Review `nexora.toml`: keep unsuffixed stable base values for `app_id`, optional
   `updater.app_id`, and `display_name`; remove any manually embedded beta or nightly suffixes.
3. Rebuild stable, beta, and nightly separately with the `v0.42.0` CLI. Stable can upgrade its
   existing directory. Beta and nightly must use their new installers and default directories;
   users then sign in and configure preferences again.
4. Do not migrate or copy legacy credentials, preferences, updater state, or logs. For a beta or
   nightly rollback, retain both old and new installation directories and select the intended
   version explicitly rather than overwriting across channels.
5. The scaffold `nexora.toml` now documents base identities. Existing projects do not need to be
   regenerated, but they should complete step 2 manually. This release does not change
   `.agents/skills`, so downstream Skill synchronization is not required.

This release does not change PostgreSQL, OIDC, object-storage, or release-signing protocols.
Integration checks requiring an external database, Identity Provider, S3/OSS credentials, real
signing certificates, or multi-host installation and upgrade environments were not run.
