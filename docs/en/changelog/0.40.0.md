# Nexora 0.40.0

Release date: 2026-08-17

## Summary

Account now keeps local accounts, ZITADEL service accounts, Project roles, and user authorizations in
one workflow. A service account can be created by username or imported after explicit confirmation
when a matching Provider machine user already exists. Role definitions and assignments are mirrored
to the ZITADEL Project. Product-level Secret/PAT management has been removed; developers create PATs
in ZITADEL while Nexora retains opaque-token introspection.

Owner: [@Jixiangup](https://github.com/Jixiangup)

Related Issue/PR: none

## Added

- Service-account creation accepts `use_existing`. A matching local or Provider machine user first
  returns `409 service_account_reuse_confirmation_required`; a matching human user returns
  `409 service_account_username_type_conflict`. — Owner: [@Jixiangup](https://github.com/Jixiangup)
- Account uses the ZITADEL v2 `AuthorizationService` to replace a user's complete role set in the
  default Project and attempts to restore the previous Provider assignment if the local write fails.
  — Owner: [@Jixiangup](https://github.com/Jixiangup)
- Custom roles owned by the system scope are created, renamed, and removed in the ZITADEL Project.
  Assignment idempotently ensures every target role first, so pre-upgrade local roles are reconciled
  on their first assignment. — Owner: [@Jixiangup](https://github.com/Jixiangup)

## Changed

- Human users, service accounts, and the default user-management UI now replace ZITADEL authorization
  before writing local `account.user_roles`; role removal follows the same complete-set operation.
  — Owner: [@Jixiangup](https://github.com/Jixiangup)
- The service-account dialog no longer offers an initial credential and uses the standard confirmation
  dialog for username reuse. — Owner: [@Jixiangup](https://github.com/Jixiangup)
- `[account.oidc].introspection_client_id` and `introspection_client_secret` remain supported for
  opaque PAT introspection. Omitting them still selects JWT-only verification.
  — Owner: [@Jixiangup](https://github.com/Jixiangup)

## Removed

- Removed the “Account and credentials” entry, credential forms, and one-time secret display.
  — Owner: [@Jixiangup](https://github.com/Jixiangup)
- Removed credential HTTP routes, client methods, public DTOs, Rust domain capabilities, Provider
  adapter methods, and `service_account_credentials` permissions.
  — Owner: [@Jixiangup](https://github.com/Jixiangup)
- A new migration drops `account.service_account_credentials` and its enums. It does not delete any
  Secret or PAT held by ZITADEL. — Owner: [@Jixiangup](https://github.com/Jixiangup)

## Compatibility and breaking changes

- This release breaks public APIs and the database schema, so the version advances from `0.39.0` to
  `0.40.0`.
- Downstream callers must remove
  `GET/POST /service-accounts/{id}/credentials`,
  `POST /service-accounts/{id}/credentials/reconcile`, and
  `DELETE /service-accounts/{id}/credentials/{credential_id}`. They now return `404`.
- Downstream Rust code must remove credential DTOs, client methods, and domain types. Service-account
  creation now sends only profile fields, roles, and optional `use_existing`; `initial_credential` no
  longer exists.
- The up migration permanently removes Nexora's non-secret credential metadata. Provider Secrets and
  PATs remain intact. The down migration recreates an empty table, enums, and permissions but cannot
  recover removed metadata.
- The ZITADEL management PAT must authorize Project-role and Project-authorization reads and writes.
  A missing capability fails the operation closed instead of silently changing only local state.
- No settings, macros, Skills, or scaffold rules were added. Introspection configuration is compatible.

## Upgrading from 0.39.0

1. Move every Nexora workspace dependency to Git tag `v0.40.0`, regenerate `Cargo.lock`, and keep the
   desktop and server on the same tag.
2. Confirm that the Account management PAT can manage ZITADEL Project roles and authorizations.
3. Run `nexora::server::migrate(&pool)` on the host's single `PgPool` before application migrations.
   The migration removes local credential metadata without deleting Provider credentials.
4. Remove application credential-management screens and HTTP calls. Developers should create PATs in
   ZITADEL and send them as Bearer tokens to application APIs.
5. Verify that role creation, rename, deletion, grant, and removal are reflected in the ZITADEL
   Project. Existing local roles are created idempotently in the Provider on first assignment.

Before rolling back to `0.39.0`, stop the new service and run the down migration. It recreates empty
credential structures but cannot restore the removed metadata; using the old credential UI again
requires reconciliation or new Provider credentials.

## Validation

The following gates ran and passed:

- SemVer parsing confirms that `0.40.0` is strictly greater than `0.39.0`
- `cargo fmt --all --check`
- `cargo check --workspace --all-features --all-targets`
- Account and migration database tests using a PostgreSQL setup URL derived from the standard
  `config/server.toml`
- `cargo test --workspace --all-targets`
- `cargo clippy --workspace --all-targets --all-features -- -D warnings`
- `cargo run -p cli -- lint --workspace . --deny-warnings`
- `bash scripts/check-scaffold-consumer.sh`
- `cd docs && bun install --frozen-lockfile && bun run build`
- OpenAPI YAML parsing and Redocly lint

A live ZITADEL write integration test was intentionally not run to avoid mutating the shared identity
directory. Provider v2 gRPC mappings, request construction, compensation paths, and local database
behavior are covered by unit and isolated database tests.

Signing, notarization, object storage, and CLI self-update assets continue through the tag-triggered
GitHub Actions workflow. Source dependencies can upgrade immediately after the `v0.40.0` tag is
pushed without waiting for those binary publishing jobs.
