# Nexora 0.38.0

Release date: 2026-08-14

## Summary

This release adds a complete non-human identity workflow to Account. Administrators can provision
ZITADEL machine users, manage service-account profiles, status, and roles in the unified user
directory, and create, rotate, or revoke Client Credentials and PATs. Secrets and PATs are returned
exactly once; Nexora persists only non-recoverable credential metadata. Bearer authentication now
combines local discovery/JWKS validation for JWTs with per-request introspection for PATs and opaque
tokens. The default desktop user page adds dedicated service-account, credential-management, and
one-time secret-delivery interactions.

Owner: [@Jixiangup](https://github.com/Jixiangup)

Related Issue/PR: none

## Added

- Added explicit `human` / `service_account` account types, an administrative description, a
  credential-metadata table, and four granular permissions. The migration classifies historical
  accounts while preserving the super administrator as a human. — Owner: [@Jixiangup](https://github.com/Jixiangup)
- Added APIs for service-account provisioning and profile updates plus credential listing,
  creation/rotation, and revocation. Public contracts, the `Account` facade, the desktop HTTP client,
  and OpenAPI expose the same resources. — Owner: [@Jixiangup](https://github.com/Jixiangup)
- Added ZITADEL machine-user, Client Secret, and PAT adapters. Credential creation uses a
  service-account-scoped `Idempotency-Key`, serializes Client Secret rotation, and compensates or
  emits stable errors when Provider changes fail. — Owner: [@Jixiangup](https://github.com/Jixiangup)
- Added a default desktop service-account FormDialog, credential panel, and one-time Secret/PAT
  display. Humans and service accounts continue to share user status and role workflows, with risky
  actions gated by permissions. — Owner: [@Jixiangup](https://github.com/Jixiangup)

## Changed

- Account Bearer verification is now composed: JWTs continue to use local discovery/JWKS validation,
  while PATs and other opaque tokens call ZITADEL `/oauth/v2/introspect` on every request without
  caching successful results. — Owner: [@Jixiangup](https://github.com/Jixiangup)
- `/me` continues to refresh human profiles from ZITADEL, but returns the local authorization
  snapshot for service accounts. Suspending a service account makes the local status gate reject its
  JWTs and PATs immediately. — Owner: [@Jixiangup](https://github.com/Jixiangup)
- User filtering now reads the explicit `user_type`. Service accounts do not receive the default
  `member` role; initial roles are caller-selected and reuse the unified replacement and implication
  rules. — Owner: [@Jixiangup](https://github.com/Jixiangup)
- The Account workspace scaffold configuration adds safe placeholders and comments for the
  introspection Client ID/Secret. This release does not change `.agents/skills`, macro rules, or the
  generated project structure, so downstream applications do not need to synchronize a new Skill.
  — Owner: [@Jixiangup](https://github.com/Jixiangup)

## Security

- Client Secret and PAT plaintext is never written to the database, logs, Debug output, or list
  responses. It is delivered once after creation; reconciliation stores only Provider IDs, types,
  timestamps, status, source, and actor metadata. — Owner: [@Jixiangup](https://github.com/Jixiangup)
- Provider outages, inactive tokens, and issuer or audience mismatches fail closed for PATs and opaque
  tokens. The introspection Secret is injected as dedicated sensitive configuration and redacted from
  Debug output. — Owner: [@Jixiangup](https://github.com/Jixiangup)

## Compatibility and breaking changes

- Server `[oidc]` configuration now requires `introspection_client_id` and
  `introspection_client_secret`. Version 0.37.0 needed only the issuer, audience, and management PAT;
  0.38.0 also initializes the PAT/opaque-token introspection verifier and fails startup when its
  resource-server credentials are missing or invalid.
- Hosts that construct `AccountDependencies` directly must add
  `service_account_directory: Option<Arc<dyn ServiceAccountDirectory>>`. Pass `None` when service
  account management is not required; ZITADEL composition uses the same `ZitadelUserDirectory` as
  the human directory.
- The migration adds PostgreSQL enums, `account.users.user_type`, `description`, indexes,
  `account.service_account_credentials`, and four permissions. Historical super administrators are
  classified as `human`; other rows with both username and email absent become `service_account`, and
  the remainder become `human`. Audit this classification before deployment.
- The new HTTP paths and DTOs are additive, but `User` adds `description` and `user_type` changes from
  an inferred to a persisted value. Required configuration, a public construction type, and data
  classification are breaking changes in the 0.x line, so the release increments MINOR.

Old configuration:

```toml
[oidc]
issuer_url = "https://identity.example.com"
audience = "nexora-api"
organization_id = "zitadel-organization-id"
project_id = "zitadel-project-id"
personal_access_token = "replace-through-secret-injection"
```

New configuration:

```toml
[oidc]
issuer_url = "https://identity.example.com"
audience = "nexora-api"
organization_id = "zitadel-organization-id"
project_id = "zitadel-project-id"
personal_access_token = "replace-through-secret-injection"
introspection_client_id = "nexora-resource-server-client-id"
introspection_client_secret = "replace-through-secret-injection"
```

Old construction:

```rust
AccountDependencies {
    pool,
    token_verifier,
    identity_directory,
}
```

New construction:

```rust
AccountDependencies {
    pool,
    token_verifier,
    identity_directory,
    service_account_directory: None,
}
```

## Upgrading from 0.37.0

1. Provision a Client ID/Secret in ZITADEL that lets the API resource server call introspection, then
   inject it through `OIDC__INTROSPECTION_CLIENT_ID` and `OIDC__INTROSPECTION_CLIENT_SECRET` or a secret
   manager. Do not reuse or commit the management PAT, Client Secret, or generated PATs.
2. Move every Nexora workspace dependency and the CLI to Git tag `v0.38.0`, remove temporary local
   path/patch entries, and regenerate `Cargo.lock`.
3. Add `service_account_directory` to direct `AccountDependencies` construction. Pass `None` when
   Provider-backed service-account management is not enabled, or reuse `ZitadelUserDirectory` for the
   complete ZITADEL workflow.
4. Back up the database and audit historical `account.users` rows whose username and email are both
   absent. On the one shared `PgPool`, run `nexora::server::migrate(&pool)`, then the application's SQLx
   Migrator, and only then call `Server::initialize`.
5. Grant administrators the appropriate `service_accounts:provision`,
   `service_accounts:profile.write`, `service_accounts:credentials.read`, and
   `service_accounts:credentials.write` permissions. Write implies read.
6. Verify JWT login, PAT introspection, suspended-service-account rejection, one-time credential
   delivery, Client Secret rotation, PAT revocation, and existing human provisioning/status/role flows.

Before rollback, revoke Client Secrets and PATs created by this version in ZITADEL and disable or
delete machine users as appropriate. Rolling back only the local database otherwise leaves orphaned
Provider credentials. Back up service-account and credential metadata, stop 0.38.0 instances, run
this migration's down script, deploy 0.37.0, and restore the old configuration. The down migration
permanently deletes all credential metadata, four permissions, explicit account types, and
descriptions; it does not revoke Provider resources. Version 0.37.0 cannot represent the new service
account data, so rollback is not lossless.

## Validation

The following gates were run and passed:

- The release test uses the `semver` crate to confirm that `0.38.0` is strictly greater than `0.37.0`
- `cargo fmt --all --check`
- `cargo check --workspace --all-targets`
- `cargo test --workspace --all-targets`
- `cargo clippy --workspace --all-targets --all-features -- -D warnings`
- `cargo run -p cli -- lint --workspace . --deny-warnings`
- `bash scripts/check-scaffold-consumer.sh`
- `cd docs && bun install --frozen-lockfile && bun run build`
- `bunx @redocly/cli lint docs/public/openapi.yaml --skip-rule operation-4xx-response`
- The Account PostgreSQL store and migration data-preservation targets compile with `database-tests`

The base PostgreSQL database configured in standard `config/server.toml` does not exist, so the real
migration/run/revert cycle and isolated `#[sqlx::test]` cases were not executed, and no alternate
database URL was used. Live ZITADEL machine-user, Client Secret, PAT, and introspection end-to-end
network tests were not run; deterministic tests cover adapter request shapes, status mapping,
fail-closed authentication, HTTP behavior, and domain rules. Signing, notarization, and object-storage
environments are outside this release scope.
