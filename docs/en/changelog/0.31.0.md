# Nexora 0.31.0

> This version was based on v0.30.1 and does not contain the concurrently released v0.30.2
> Windows Inno fixes. Use v0.31.1 instead.

Release date: 2026-08-07

## Summary

This release fixes the framework baseline from Nexora v0.29.0 through v0.30.1 failing on an empty
PostgreSQL 17 database. The new Account baseline preserves every `NOT NULL` data constraint and
column comment, but no longer names column-level `NOT NULL` constraints that are registered as
independent `pg_constraint` objects only by PostgreSQL 18, nor attempts to annotate those objects
with `COMMENT ON CONSTRAINT`.

Owner: [@Jixiangup](https://github.com/Jixiangup)

Related issue/PR: none

## Fixed

- Fixed the first framework migration failing on PostgreSQL 17 at
  `COMMENT ON CONSTRAINT users_id_not_null` with
  `constraint "users_id_not_null" for table "users" does not exist`, which prevented a fresh
  database from starting. — Owner: [@Jixiangup](https://github.com/Jixiangup)
- Added migration-source regression coverage that rejects named column-level `NOT NULL`
  constraints and their constraint comments while confirming key columns remain `NOT NULL`.
  — Owner: [@Jixiangup](https://github.com/Jixiangup)
- Fixed the Windows invalid Inno Setup path fixture failing while creating its temporary directory
  before it reached production validation. The test now exercises the path-definition boundary
  directly. — Owner: [@Jixiangup](https://github.com/Jixiangup)

## Changed

- Regenerated the four reversible timestamp framework baselines through the SQLx CLI. Account
  tables, permission catalogs, protection functions, indexes, and seeded permission semantics are
  unchanged. — Owner: [@Jixiangup](https://github.com/Jixiangup)
- Documented PostgreSQL 17 as the minimum supported database version for framework migrations and
  established `NOT NULL` plus `COMMENT ON COLUMN` as the portable representation.
  — Owner: [@Jixiangup](https://github.com/Jixiangup)

## Compatibility and breaking changes

This release establishes the framework SQLx baseline again and is therefore migration-breaking:

- `nexora._sqlx_migrations` from v0.29.0, v0.30.0, and v0.30.1 is incompatible with v0.31.0.
- Do not rewrite old checksums, delete only the old history table and run against the existing
  schema, or restore old DDL.
- Existing deployments must preserve required business data and rebuild an empty database. The new
  database still runs `nexora::server::migrate(&pool)` before the application migrator.
- HTTP APIs, Account DTOs, authentication and authorization semantics, desktop UI, updater protocol,
  and the `nexora.toml` schema are unchanged.

## Upgrading from 0.30.1

1. Stop the old service, back up the database and retained business data, and verify that the
   v0.30.1 database snapshot can be restored.
2. Update all Nexora workspace dependencies to `0.31.0` or Git tag `v0.31.0`, regenerate the
   lockfile, and reinstall the v0.31.0 CLI.
3. Drop the old database and create an empty UTF-8 database. Do not delete only the
   `account`/`nexora` schemas or migration history.
4. Run the Nexora v0.31.0 framework migrator on the host pool, then run the application migrator.
5. Restore only approved business data through an audited import. Do not restore old migration
   history, DDL, or checksums.

Rolling back to v0.30.1 requires restoring the pre-upgrade v0.30.1 binary, dependencies, lockfile,
and database snapshot together. v0.31.0 down migrations are not a legacy-history conversion tool.

## Validation

The following checks currently pass:

- `cargo fmt --all --check`
- `cargo test --workspace --all-targets --locked`
- `cargo clippy --workspace --all-targets --all-features --locked -- -D warnings`
- `cargo run -p cli --locked -- lint --workspace . --deny-warnings`
- `cargo test -p migrate --all-features --test data_preservation`
- `cargo test -p account --no-default-features --features database-tests --test postgres_store`
- `installed_inno_setup_reports_pinned_engine_version` against a real Inno Setup 6.7.3 install
- `scripts/check-scaffold-consumer.sh`
- `bun install --frozen-lockfile && bun run build` in `docs/`
- Full framework migration `run` on an isolated empty PostgreSQL 17 database
- Repeated `run` against the same database
- `migrate info`
- `revert latest` followed by `run`

This release does not change Skills or scaffold structure. Downstream projects only need the new
version and the database rebuild procedure above.
