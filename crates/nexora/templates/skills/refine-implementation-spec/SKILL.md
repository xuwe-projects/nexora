# 澄清需求并编写实施规格

将设计决策与代码实施分开。先理解仓库现状和用户意图，再产出可以脱离当前对话独立使用的实施规格。

## 守住阶段边界

- 在规格阶段不编辑文件、不生成迁移、不更新依赖、不提交代码，也不执行会改变工作区或外部系统的命令。
- 允许读取源码、测试、配置、文档、版本历史和相关 Skill，以验证现状与约束。
- 用户明确要求“直接实现”、“按已确认规格实施”或同等意思时，不把请求强制拉回规格阶段。
- 用户在澄清期间要求开始实现时，先简要复述已确认范围和剩余假设，再转入实施。

## 执行工作流

### 1. 建立已验证上下文

先用只读方式检查与请求直接相关的页面、组件、状态、路由、数据模型、API、数据库、测试和仓库规则。调研深度与任务风险相称，不对无关模块做全面盘点。

记录三类信息，不得混淆：

- **已验证事实**：能从代码、配置、测试或用户陈述直接确认。
- **建议决策**：需要用户确认的产品或技术选择。
- **暂定假设**：当前证据不足，但可以在明确标注后继续讨论的内容。

不要把未打开的文件、未验证的 API 或想象中的架构写成仓库现状。

### 2. 找出会改变结果的歧义

只追问会实质改变以下内容的问题：

- 用户可见行为、交互、默认值或错误处理。
- 数据语义、权限、兼容性、持久化或 API 契约。
- 实现范围、方案取舍、验收标准或发布风险。

每轮聚焦少量高价值问题。对每个问题说明它影响什么，给出推荐选项及理由；不要把所有可想象的细节一次性丢给用户。

对可以从现有约定安全推导的小细节，直接提出标注清楚的默认建议，不要用低价值问题拖慢讨论。

### 3. 共同收敛方案

随着对话更新简短的“已确认决策”和“待确认项”。需要取舍时：

- 先给出最简单、最符合现有架构的推荐方案。
- 解释关键代价，包括产品体验、数据正确性、复杂度、兼容性和测试成本。
- 如果用户方案与仓库已有契约冲突，用具体证据指出，不要默默迎合。
- 避免为了让文档显得完整而提前设计未被需求驱动的抽象、配置项或扩展点。

当阻塞性歧义已清空时，生成一份标记为“待确认”的完整规格，并请用户确认或指出需要修订的章节。不得把用户沉默当作确认。

### 4. 输出最终可交接规格

只有用户明确确认待确认稿后，才输出标记为“已确认”的最终版。最终版必须能直接复制给没有参与前序对话的实施智能体，不得出现“如上所述”、“按我们刚才讨论”等依赖会话历史的表达。

使用一个完整的 Markdown 代码块包裹规格，方便复制。根据任务删除确实不适用的可选章节，但至少包含：

1. **任务标题与状态**：明确标注已确认。
2. **目标与背景**：解决什么问题，当前已验证的行为是什么。
3. **需求**：按可观察行为描述必须完成的功能和交互。
4. **实施方案**：指明应复用和修改的现有边界、数据流、状态归属及关键契约，不伪造未调研的精确符号。
5. **约束**：仓库规则、兼容性、权限、性能、数据和界面约束。
6. **不做**：排除相邻但未被授权的功能、重构和抽象。
7. **边界与注意点**：空状态、加载、失败、权限、并发、数据一致性和兼容行为中适用的部分。
8. **验收标准**：使用可观察、可判定的条件，覆盖正常路径和关键边界。
9. **验证方式**：需要新增或更新的测试，以及应执行的范围相称检查。
10. **交付要求**：限制扩大范围，要求报告改动、验证结果和剩余风险。

仅在适用时增加：

- **Bug 修复**：复现条件、实际结果、期望结果、有证据的根因、回归测试。
- **API 或数据变更**：请求/响应契约、迁移、兼容性、授权和错误语义。
- **界面变更**：位置、组件、交互时序、文案以及 loading/empty/error/disabled 状态。

最终版不得保留未解决的阻塞性问题。非阻塞假设可以保留，但必须对实施智能体明确说明如何验证，以及验证失败时应停下请求决策还是可以采用哪个安全默认值。

## 质量检查

输出待确认稿或最终稿前检查：

- 另一个智能体在看不到当前对话时，是否仍知道要改什么、为什么改、改到什么程度。
- 每项方案是否来自已验证现状或明确决策，而不是隐藏猜测。
- 需求、约束、不做和验收标准之间是否一致。
- 执行智能体是否可以通过测试和可观察结果判断完成，而不是依赖主观词语。
- 文档是否约束了结果和必要的架构边界，同时没有把无关实现细节锁死。
- 是否明确禁止无关重构、猜测性功能和未验证的范围扩张。
